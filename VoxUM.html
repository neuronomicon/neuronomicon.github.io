Before you start

What you need on disk

  • Unity 6 with Windows Build Support. The project targets StandaloneWindows64.
  • ML-Agents Unity package installed, plus the matching Python package in a conda or venv environment.
  • The compiled Voxelyze DLL. Build the C++ solution first — Unity loads it through VoxelDllConfig.DLL_NAME. Nothing in this guide works without it.
  • A .vox robot file in StreamingAssets. This guide uses Test_V33_M33_All_Motor.vox — 33 voxels, all of them muscle.
Rebuild If you change any C++ source, rebuild the DLL and copy it into the Unity project. Editing the source alone leaves the old binary loaded, and the symptoms look like Unity bugs rather than a stale DLL.
Concept

How the control loop works

Read this before touching the scene. The timing model is the one thing here that differs from a stock ML-Agents project, and almost every setup mistake traces back to it.

Physics runs on a background C++ thread, asynchronously. Unity cannot simply step the Academy on a fixed schedule and hope the physics kept up — it has to wait for the worker to finish, then hand over the next batch of actions. So VoxelRLManager disables automatic stepping and drives the whole cycle by hand from Update().

Never Do not add a Decision Requester component. It would request decisions on Unity's own schedule, independent of the C++ worker, and break the lock-step: agents would submit actions while physics is mid-flight. The manager calls RequestDecision() for every agent itself. If you find one on a robot, remove it.

Why time_scale barely helps here

In a stock ML-Agents project the Academy steps from FixedUpdate, so raising time_scale multiplies throughput. This project steps from Update(), which fires once per rendered frame regardless of time scale. The knob that actually matters is target_frame_rate: -1, which uncaps the frame rate. Leave time_scale at 1 — see step 7.

Step 1

Scene skeleton

One object owns the engine, the robot builder, and the RL clock for the whole scene.

  1. Create an empty GameObject at the scene root and name it VoxelEngineManager.
  2. Add these three components, in this order:
    • VoxelEngineCore — loads the DLL, boots the C++ engine, indexes robots
    • VoxelRobotBuilder — parses .vox files and sends the blueprint to C++
    • VoxelRLManager — drives the lock-step decision cycle
  3. On VoxelEngineCore, set Dll Folder Path to the folder holding your built DLL, or use the editor menu Voxel Engine ▸ Select DLL File.
  4. Tick Is Ml Agent. This one checkbox switches the scene between training mode and plain physics-playback mode.

VoxelRLManager timing

FieldValueMeaning
stepsPerSimulationCycle20 C++ micro-steps per cycle. 20 × 1 ms = 0.02 s, i.e. 50 Hz decisions.
customDecisionPeriod1 Cycles per PPO decision. 1 means decide every cycle.
actionSizePerRobotauto Read-only. Derived from the Body Profile at startup — never type it in.

50 Hz is the standard rate for locomotion RL. For a robot with a ~2 Hz gait that is about 25 decisions per gait cycle, enough for the policy to shape a waveform rather than flip a switch.

Step 2

Training area

Each robot trains in its own isolated arena. The project ships a prefab called TrainingAreaVox — start from it rather than assembling one by hand.

TrainingAreaVox ← VoxelPhysicsManager ├── Plane floor ├── Cube / Sphere rigid obstacles (Rigidbody + Collider) ├── TargetCylinder the goal the robot chases ├── VoxRobot_00 ← the RL robot └── VoxRobot_01 companion, no agent

VoxelPhysicsManager on the arena root relays rigid-body collisions between Unity PhysX and the Voxelyze soft bodies, and hands out robot indices at startup.

Companion VoxRobot_01 is a small test body with no VoxelRobotAgent. It gets simulated but never receives actions — useful for checking multi-robot interaction. Because it still occupies a simulation slot, an arena costs two robots in the C++ thread budget, not one. That matters when you scale up.

Drag any interactive rigid bodies into the Interactive Objects array on VoxelPhysicsManager so their collisions reach the soft body.

Step 3

Robot object

Select VoxRobot_00. It carries five components:

ComponentRole
VoxelRobotInstanceWhich .vox file to load, and how many inner OpenMP threads this robot gets
VoxelPhysicsInfoZero-GC bridge to the C++ voxel state buffer
VoxelGraphicRendererDraws the deforming mesh from the triple buffer
VoxelRobotAgentThe ML-Agents agent. Thin — it delegates everything to the Task Profile
BehaviorParametersAdded automatically with the agent

Set Selected Vox File Name on VoxelRobotInstance to Test_V33_M33_All_Motor.vox, and threadCount to 3 for now.

Leave alone robotIdx on the agent is assigned at runtime by InitializeArea(), which numbers every robot sequentially across all arenas. Whatever value is serialized in the prefab is overwritten. Don't try to set it by hand.
Step 4

Body Profile

The robot's body and its task are separate assets. A Body Profile describes anatomy and is reusable across every task you write for that robot.

Create one with Create ▸ RL Bodies ▸ Voxel Robot Body. For the shipped 33-voxel robot:

FieldValueMeaning
expectedVoxelCount33Voxels included in the observation
muscleCount33Actuated voxels — this is the action count
centerVoxelIdx16Kept for reference; the observation uses the centre of mass
forwardVoxelA / B17 / 15Voxel pair defining the local forward axis
rightVoxelA / B21 / 11Voxel pair defining the local right axis
includeVoxelAngVelfalseOff → 240 observations. On → 339
targetDistScale5Divisor that normalises target distance
Critical muscleCount must equal the number of is_muscle voxels in your .vox file. Set it too low and the surplus muscles are never commanded — part of the robot simply hangs limp, and nothing reports an error. The filename convention helps: V33_M33 means 33 voxels, 33 muscles.

What the observation contains

Everything is expressed in a body-local frame built from the two voxel pairs above, and measured relative to the centre of mass — so the policy sees the same numbers wherever the robot happens to be standing.

IndexContentsCount
0–2Target direction (unit x, z) and normalised distance3
3–5Centre-of-mass velocity, local frame3
6–8Mean angular velocity, local frame3
9–206Per voxel: position and velocity relative to CoM6 × 33
207–239Previous action33

That last block matters more than it looks. The actuators have a first-order lag (τ ≈ 50 ms), so what the robot does next depends on commands it received a few steps ago. Feeding the previous action back in restores the Markov property — without it the policy is guessing at hidden state.

Step 5

Task Profile

A Task Profile holds the objective: rewards, termination, episode length. Create one with Create ▸ RL Tasks ▸ Target Tracking.

  1. Drag your Body Profile into the Body slot.
  2. Set maxStep to 500 — at 50 Hz that is a 10-second episode.
  3. Leave behaviorName as VoxBot33; it must match the key in your training YAML.
  4. Select VoxRobot_00 and drag the Task Profile into the agent's Task Profile slot.
  5. A Runtime State block appears. Drag the arena's TargetCylinder into Target Transform.

Reward shape

TermValueWhen
distance2.0 × ΔdEvery step. d is horizontal (XZ) distance to the target
success+5.0Within 0.2 of the target — episode ends
fall / flip−1.0CoM below −2.0, or the body's up axis inverts
freeze−1.0No movement for 125 steps (2.5 s)
time−1 / maxStepEvery surviving step, so dawdling costs
Note Distance is measured in the horizontal plane only. Vertical distance is deliberately excluded — otherwise the robot could earn reward by inflating upward toward a target floating above it, and could never satisfy the reach threshold while standing under it.

How actions reach the muscles

The policy outputs one continuous value per muscle voxel in [-1, +1]. That maps linearly to a voxel temperature, which drives thermal expansion or contraction:

−1.0 → −12 °  contract 0 → neutral +1.0 → +12 °  expand

The C++ side does not apply that target instantly. Each 1 ms micro-step moves the current temperature 2 % of the way toward it, giving a first-order actuator with τ ≈ 49.5 ms. That is what keeps a jumpy policy from exploding the mass-spring solver — and it is why the previous action belongs in the observation.

Step 6

Check the numbers

Observation and action sizes are derived, not typed. The agent pushes them into BehaviorParameters from the profiles. Your job is to confirm they landed.

Open Behavior Parameters on VoxRobot_00 and verify:

FieldExpected
Vector Observation ▸ Space Size240
Vector Observation ▸ Stacked Vectors1
Actions ▸ Continuous Actions33
Behavior NameVoxBot33
Decision Requester componentabsent
Prefab If your robots are prefab instances, fix these on the prefab, not on one instance. ML-Agents builds the vector sensor from the serialized value before Initialize() runs, so a stale prefab value can win. Touch the Task Profile asset in Prefab Mode to trigger the sync, then save the prefab.

Where 240 comes from: 9 + 6 × 33 for the body state, plus 33 for the previous action. Turn on includeVoxelAngVel and it becomes 9 + 9 × 33 + 33 = 339. Either is fine — but a trained model is tied to whichever you used.

Step 7

Training config

Save this as VoxBot33.yaml. The behavior key must match behaviorName.

behaviors:
  VoxBot33:
    trainer_type: ppo
    hyperparameters:
      batch_size: 2048
      buffer_size: 20480
      learning_rate: 0.0003
      beta: 0.005
      epsilon: 0.2
      lambd: 0.95
      num_epoch: 3
      learning_rate_schedule: linear
    network_settings:
      normalize: true          # essential — raw voxel units vary in scale
      hidden_units: 512
      num_layers: 3
    reward_signals:
      extrinsic:
        gamma: 0.995           # 200-step horizon ≈ 4 s of the 10 s episode
        strength: 1.0
    keep_checkpoints: 5
    checkpoint_interval: 500000
    max_steps: 10000000
    time_horizon: 256          # ≥ maxStep, so each episode is one trajectory
    summary_freq: 10000

engine_settings:             # top level — NOT nested under the behavior
  time_scale: 1
  target_frame_rate: -1
  no_graphics: false
  quality_level: 0
Indent engine_settings sits at column 0, a sibling of behaviors. Nest it under VoxBot33 and ML-Agents aborts with The option engine_settings … is invalid.

max_steps counts agent steps summed across every robot. With four robots, 10 M total is 2.5 M per robot — worth remembering when reading TensorBoard.

Step 8

Run it

  1. In your Python environment: 
    mlagents-learn config/VoxBot33.yaml --run-id=VoxBot_01
  2. Wait for Listening on port 5004, then press Play in Unity.
  3. Watch the console. These two lines tell you the wiring is correct: 
    [VoxelEngineCore] Total 2 robots indexed sequentially across 1 training areas.
[VoxelRLManager] 1 robots, actionSize=33

Two robots indexed, one RL robot — the second is the companion. If both show as RL robots, the companion has an agent component on it that should not be there.

First ten minutes on TensorBoard

Cumulative RewardNoisy but moving Flat at zero → actions aren't reaching the muscles

Tip Before training, test the wiring by hand. Set Behavior Type to Heuristic Only and hold A or D — the built-in heuristic drives each muscle with a phase-shifted sine, so the robot should visibly crawl. If it only puffs up uniformly or does nothing, fix that before you spend GPU hours.
Going wider

Scaling up

Three scenes ship with the project. More arenas collect experience faster and give PPO a more decorrelated batch.

SceneArenasSim robotsOuter threads
SingleArenaScene122
MultiArenaScene04488
MultiArenaScene16163232
Threads Total threads = robots × per-robot threadCount. With 16 arenas and threadCount: 3 on the RL robot you are at 64 threads before Unity's own. Oversubscribe a 64-core machine and 16 arenas will run slower than 4. Drop threadCount to 2 in the 16-arena scene.

Keep the YAML identical across scenes. buffer_size counts total agent steps, so the number of policy updates at a given step count is the same either way — which is exactly what makes a 4-vs-16 comparison meaningful. Changing hyperparameters at the same time confounds the result.

Optional

Standalone builds

Training against a built player is faster than the editor. Open VoxUnityML ▸ Auto Build (Client & Server), pick a scene, and press the button — it produces a graphics build and a headless server build in one pass. 

VoxUnityML_Auto_Builds/
└── MultiArenaScene04/
    ├── GraphicMode/VoxelSim_Graphics.exe
    └── ServerMode/VoxelSim_Server.exe

Point the trainer at one with --env: 

mlagents-learn config/VoxBot33.yaml --run-id=VoxBot_02 \
  --env=../VoxUnityML_Auto_Builds/MultiArenaScene04/ServerMode/VoxelSim_Server.exe

Only then does no_graphics in the YAML do anything — in the editor it is ignored. Everything else comes from your current Player Settings and the Build Profiles checkboxes.

When it breaks

Troubleshooting

Failed to load PlayerSettings (internal index #0)
The build folder holds files from two different builds. Delete the output folder entirely and rebuild — Unity never cleans it for you. The bundled AutoBuilder now does this automatically.
The option engine_settings … is invalid
engine_settings is indented under the behavior. Move it to column 0, level with behaviors.
Observation size mismatch
BehaviorParameters disagrees with what CollectObservations writes. Nearly always a stale prefab value — see step 6. Confirm 240 (or 339 with angular velocity on).
Only part of the robot moves
muscleCount is smaller than the real number of muscle voxels. Voxels beyond the count keep a target of zero forever. Check it against the .vox file.
Nothing moves at all, and training never starts
The lock-step is stalled. VoxelRLManager waits for every agent to submit before stepping C++, so one agent with a missing Task Profile or a null manager reference freezes the whole scene. Check the console count matches the arenas you expect.
Robot explodes or twitches violently
Lower TEMP_MAX in Apply_RL_Actions_To_Motors_Direct_Temperature_Control from 12 to 6–8 and rebuild the DLL. Early in training the policy is nearly random, and neighbouring voxels pulling in opposite directions is the worst case for a mass-spring solver.
Episodes end almost immediately
Flip detection is working, possibly too well. It compares the body's up axis against world up; soften it by requiring a deeper tilt, or raise freezeStepLimit if the freeze check is the one firing.

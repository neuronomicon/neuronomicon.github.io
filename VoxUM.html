Before you start

What you need on disk

  • Unity 6 with Windows Build Support. The project targets StandaloneWindows64.
  • ML-Agents Unity package installed, plus the matching Python package in a conda or venv environment.
  • The compiled Voxelyze DLL. Build the C++ solution first. Unity loads it by the name in VoxelDllConfig.DLL_NAME, which ships as NeuronomicoN_DLL_x64_Release. Nothing in this guide works without it.
  • A .vox robot file in StreamingAssets. This guide uses Test_V33_M33_All_Motor.vox — 33 voxels, all of them muscle.

Every component, asset and menu named below already exists in the project. You are wiring existing pieces together, not writing code.

Rebuild If you change any C++ source, rebuild the DLL and make sure the folder Unity points at holds the new binary. Editing the source alone leaves the old DLL loaded, and the symptoms look like Unity bugs rather than a stale DLL.
Silent serial If you build the DLL with clang-cl (the ReleaseCL configuration), the OpenMP flag is /openmp — not -fopenmp. clang-cl discards -fopenmp as an unknown argument, and clang then ignores every #pragma omp without a single warning: the build succeeds and you get a completely serial DLL that looks like a Unity performance problem. That configuration also needs libomp.lib linked and libomp.dll beside the output. A compile-time guard in VoxOmpCompat.h now fails the build when _OPENMP is undefined, and the boot line rt=libomp(clang) or rt=vcomp(MSVC) tells you which runtime is actually live.
Read this first

Two length units live in this project

This is the single most common source of silent, hard-to-find mistakes, and it is worth two minutes before you touch anything. The C++ engine works in its own sim units. Unity displays the robot ten times larger.

Which side is a given number on?

QuantityUnitWhy
Voxel pos, vel from the DLLsimStraight out of the C++ state buffer
Centre of mass, previousDistancesimAveraged from those voxels
InverseTransformPoint(target.position)simThe runtime scale of 10 already divides it
targetReachThreshold, fall height, targetDistScalesimCompared against the values above

Why it bites A threshold of 0.2 looks like 20 cm and is in fact 2 metres. With targets spawning 2.5–3.5 m away, the robot is declared a winner after covering a third of the distance, and the policy learns nothing useful. The same arithmetic made an early fall check of −2.0 mean −20 m, a condition that never once fired. Both are fixed in the shipped assets — the values in step 5 are the correct ones. Whenever you add a constant, write the unit in a comment next to it.
Concept

How the control loop works

Read this before touching the scene. The timing model is the one thing here that differs from a stock ML-Agents project, and almost every setup mistake traces back to it.

Physics runs on a background C++ thread, asynchronously. Unity cannot simply step the Academy on a fixed schedule and hope the physics kept up — it has to wait for the worker to finish, then hand over the next batch of actions. So VoxelRLManager sets Academy.Instance.AutomaticSteppingEnabled = false and drives the whole cycle by hand from Update().

Never Do not add a Decision Requester component. It would request decisions on Unity's own schedule, independent of the C++ worker, and break the lock-step: agents would submit actions while physics is mid-flight. The manager calls RequestDecision() for every agent itself. If you find one on a robot, remove it.

The first 1.5 seconds

VoxelRLManager waits 1.5 s of unscaled real time before the first decision, so the Python socket has time to settle, then logs Python connection stabilized ready!. A scene that sits still for a second and a half at the start of play is behaving correctly.

Why time_scale barely helps here

In a stock ML-Agents project the Academy steps from FixedUpdate, so raising time_scale multiplies throughput. This project steps from Update(), which fires once per rendered frame regardless of time scale. The knob that actually matters is target_frame_rate: -1, which uncaps the frame rate. Leave time_scale at 1 — see step 7 and Modes & frame rate.

Step 1

Scene skeleton

One object owns the engine, the robot builder, and the RL clock for the whole scene. If you open SingleArenaScene it is already there, named VoxelEngineManager — open it and read along rather than building a new one.

  1. Create an empty GameObject at the scene root and name it VoxelEngineManager.
  2. Add these three components, in this order:
    • VoxelEngineCore — loads the DLL, boots the C++ engine, indexes robots
    • VoxelRobotBuilder — parses .vox files and sends the blueprint to C++
    • VoxelRLManager — drives the lock-step decision cycle
  3. On VoxelEngineCore, click the DLL-Dir button next to DLL Path and pick the folder holding your built DLL. The path field is read-only by design; the button is how you set it.
  4. Tick Is Ml Agent. This one checkbox switches the scene between training mode and plain physics-playback mode, and it enables or disables every Agent and BehaviorParameters in the scene for you.

Active Dll Name, Num Robots, Voxel Parse Kind and Max Num Oscillators are read-only readouts. They fill themselves in; you never type into them.

VoxelRLManager timing

FieldValueMeaning
stepsPerSimulationCycle20 C++ micro-steps per cycle. 20 × 1 ms = 0.02 s, i.e. 50 Hz decisions.
customDecisionPeriod1 Cycles per PPO decision. 1 means decide every cycle. Raise it and physics keeps running on the previous action.

50 Hz is the standard rate for locomotion RL. For a robot with a ~2 Hz gait that is about 25 decisions per gait cycle, enough for the policy to shape a waveform rather than flip a switch.

Order Set VoxelEngineCore to −1000 in Project Settings ▸ Script Execution Order. It makes the DLL path and the console hook land before anything else initialises, which matters for standalone builds — see Troubleshooting.
Step 2

Training area

Each robot trains in its own isolated arena. The project ships a prefab called TrainingAreaVox — start from it rather than assembling one by hand.

TrainingAreaVox ← VoxelPhysicsManager ├── Plane floor ├── Cube / Sphere rigid obstacles (Rigidbody + Collider) ├── TargetCylinder the goal the robot chases ├── VoxRobot_00 ← the RL robot └── VoxRobot_01 companion, no agent

VoxelPhysicsManager on the arena root relays rigid-body collisions between Unity PhysX and the Voxelyze soft bodies, and hands out robot indices at startup through InitializeArea(). Its simScale must stay at 10, matching the renderer — see Two length units.

Companion VoxRobot_01 is a small test body with no VoxelRobotAgent. It gets simulated but never receives actions — useful for checking multi-robot interaction. Because it still occupies a simulation slot, an arena costs two robots in the C++ thread budget, not one. That matters when you scale up.

Drag any interactive rigid bodies into the Interactive Objects array on VoxelPhysicsManager so their collisions reach the soft body.

Step 4

Body Profile

The robot's body and its task are separate assets. A Body Profile describes anatomy and is reusable across every task you write for that robot. The project ships RobotBody_Vox33 — use it, or create your own with Create ▸ RL Bodies ▸ Voxel Robot Body.

FieldVox33Meaning

Critical muscleCount must equal the number of is_muscle voxels in your .vox file. Set it too low and the surplus muscles are never commanded — part of the robot simply hangs limp, and nothing reports an error. The filename convention helps: V33_M33 means 33 voxels, 33 muscles.

What the observation contains

Everything is expressed in a body-local frame built from the two voxel pairs above, and measured relative to the centre of mass — so the policy sees the same numbers wherever the robot happens to be standing.

IndexContentsCount
0–2Target direction in the horizontal plane (unit x, z) and distance / targetDistScale, clipped at 23
3–5Centre-of-mass velocity, local frame3
6–8Mean angular velocity, local frame3
9–206Per observed voxel: position and velocity relative to CoM6 × 33
207–239Previous action33

That last block matters more than it looks. The actuators have a first-order lag (τ ≈ 50 ms), so what the robot does next depends on commands it received a few steps ago. Feeding the previous action back in restores the Markov property — without it the policy is guessing at hidden state. AddActuatorObservations() appends it for you; any custom task profile must call it last.

Subset observedVoxelIndices exists for bodies with large rigid regions, where most voxels carry no information but still get amplified by normalize: true. Vox33 is all muscle, so leave it empty. The appendix shows why a 516-voxel body needs it.
Step 5

Task Profile

A Task Profile holds the objective: rewards, termination, episode length. The shipped one is TargetTracking_Vox33; new ones come from Create ▸ RL Tasks ▸ Target Tracking.

  1. Drag your Body Profile into the Body slot.
  2. Set maxStep to 500 — at 50 Hz that is a 10-second episode.
  3. Leave behaviorName as VoxBot33; it must match the key in your training YAML.
  4. Select VoxRobot_00 and drag the Task Profile into the agent's Task Profile slot.
  5. A Runtime State block appears on the agent. Drag the arena's TargetCylinder into Target Transform.
Per instance Target Transform lives on the agent's runtime state, not on the shared asset. Every arena you duplicate needs its own target dragged in. A null slot skips the entire distance-reward block with no error — the run simply never learns.

Diagnostic A run that sits at exactly Mean Reward: -0.200 with Std: 0.000 is the time penalty and nothing else: every episode runs its full 500 steps and no other term ever fires. That is the signature of a robot that isn't moving, not of bad hyperparameters. Watch previousDistance in the runtime state during Play before you touch the YAML.

How actions reach the muscles

The policy outputs one continuous value per muscle voxel in [-1, +1]. The C++ side (Apply_RL_Actions_To_Motors_Direct_Temperature_Control) clamps it and maps it linearly to a voxel temperature, which drives thermal expansion or contraction:

−1.0 → −12 °  contract 0 → neutral +1.0 → +12 °  expand

The target is not applied instantly. Each 1 ms micro-step moves the current temperature ALPHA = 2 % of the way toward it, giving a first-order actuator with τ ≈ 49.5 ms. On top of that, the first 0.25 s of every episode ramps the signal from 0 to full, so a reset never slams the solver. That lag is what keeps a jumpy policy from exploding the mass-spring system — and it is why the previous action belongs in the observation.

Check the numbers

Observation and action sizes are derived, not typed. ApplyProfileSettingsToComponents() pushes them into BehaviorParameters from the profiles whenever an asset changes or the game starts. Your job is to confirm they landed.

Open Behavior Parameters on VoxRobot_00 and verify:

FieldExpected

Prefab If your robots are prefab instances, fix these on the prefab, not on one instance. ML-Agents builds the vector sensor from the serialized value before Initialize() runs, so a stale prefab value can win. Touch the Task Profile asset in Prefab Mode to trigger the sync, then save the prefab.

Where 240 comes from: 9 + 6 × 33 for the body state, plus 33 for the previous action. Turn on includeVoxelAngVel and it becomes 9 + 9 × 33 + 33 = 339. Either is fine — but a trained model is tied to whichever you used.

In general: obs = 9 + perVoxel × observedVoxels + muscleCount, where perVoxel is 6 or 9, and observedVoxels is the subset length if you set one, otherwise expectedVoxelCount.

Training config

Save this as VoxBot33.yaml. The behavior key must match behaviorName.

behaviors:
  VoxBot33:
    trainer_type: ppo
    hyperparameters:
      batch_size: 2048
      buffer_size: 20480
      learning_rate: 0.0003
      beta: 0.005
      epsilon: 0.2
      lambd: 0.95
      num_epoch: 3
      learning_rate_schedule: linear
    network_settings:
      normalize: true          # essential — raw voxel units vary in scale
      hidden_units: 512
      num_layers: 3
    reward_signals:
      extrinsic:
        gamma: 0.995           # 200-step horizon ≈ 4 s of the 10 s episode
        strength: 1.0
    keep_checkpoints: 5
    checkpoint_interval: 500000
    max_steps: 10000000
    time_horizon: 256          # ≥ maxStep, so each episode is one trajectory
    summary_freq: 10000

engine_settings:             # top level — NOT nested under the behavior
  time_scale: 1
  target_frame_rate: -1
  no_graphics: false
  quality_level: 0
Indent engine_settings sits at column 0, a sibling of behaviors. Nest it under VoxBot33 and ML-Agents aborts with The option engine_settings … is invalid.

max_steps counts agent steps summed across every robot. With four robots, 10 M total is 2.5 M per robot — worth remembering when reading TensorBoard.

Sizing hidden_units: 512 and num_layers: 3 suit the 240-dimensional Vox33 observation. A body with a reduced observation subset does not need that capacity; 256 × 2 is a better starting point there.

  1. In your Python environment:

  3. Watch the console. These lines tell you the wiring is correct:

Reference

Modes and frame rate

Because one rendered frame is one decision cycle, the frame rate cap is the training speed cap. VoxelEngineCore forces vSyncCount = 0 at startup — otherwise the monitor refresh rate would silently set your simulation speed — and then picks a cap by mode:

SituationtargetFrameRateWhy
Training or inference with Python connected−1Uncapped; matches target_frame_rate: -1 in the YAML
Headless build−1No screen, nothing to spare
ONNX inference, no Python, watching itinferenceWatchFps (50)The only case where a real-time cap is meaningful: 1000 / (20 × 1 ms) = 50 fps is real time
is_ml_agent off — free runningfreeRunRenderFps (60)Physics free-runs in C++; the cap only saves GPU

Both fps fields sit under Frame Rate Policy on VoxelEngineCore. You normally leave them alone.

Going wider

Sizing for your CPU

More arenas collect experience faster and give PPO a more decorrelated batch. How many you can actually run is decided by your CPU's physical core count — not its thread count — and on Windows by how those cores are split into processor groups. Get this wrong and 16 arenas run slower than 4.

Physical cores are the budget

Every robot is handed a contiguous block of physical cores that it owns exclusively. Two robots never share a physical core. That rule is not tidiness: all robots are joined by the macro barrier on every micro-step, so one robot waiting on a contended core drags the entire scene down with it.

Inside a robot's block, the default placement policy (VX_TPC_ADAPTIVE) spreads its threads one per physical core and leaves the SMT siblings empty for Unity, Python and the OS. If a robot cannot find enough contiguous cores, only that robot falls back to packing two threads onto one core — a local slowdown, much cheaper than letting two robots collide. 

physical core 5 = logical CPU 10, 11
physical core 6 = logical CPU 12, 13
physical core 7 = logical CPU 14, 15

spread  (default, threadCount 3)      packed  (fallback, same robot)
  cpu[0] outer -> CPU 10                cpu[0] -> CPU 10 ┐ core 5 shared
  cpu[1] inner -> CPU 12                cpu[1] -> CPU 11 ┘
  cpu[2] inner -> CPU 14                cpu[2] -> CPU 12   core 6
  CPU 11, 13, 15 free for Unity          1 core saved, that robot runs slower

So a 64-core / 128-thread machine gives you a budget of 64, not 128. The spare logical CPUs are not capacity you can spend on physics; they are the headroom that keeps Unity's frame time sane.

A block cannot cross a processor group

Windows puts at most 64 logical CPUs in a processor group, so a 64-core / 128-thread machine is two groups of 32 physical cores. A thread's affinity mask is 64 bits wide and therefore lives in exactly one group. When a robot's block doesn't fit in what remains of the current group, the allocator jumps to the start of the next one and the leftover cores are stranded — reported as skipped.

Design rule Make the core count of one training area a divisor of the per-group core count. Then nothing is stranded, every group tiles exactly, and the formula below is not an estimate but the answer. On a 64-core machine the per-group count is 32, so aim for an arena costing 1, 2, 4, 8, 16 or 32 cores.

The formula

c_i = ceil( t_i / S )          # physical cores robot i needs
C   = Σ c_i                   # physical cores one training area needs

N   = floor( (G × P − R) / C )                   # core-limited arena count
N   = min( N, floor(128 / robots_per_area) )     # hard robot ceiling
SymbolMeaningWhere to read it
PPhysical cores per processor groupphysicalCores ÷ groups in the boot log
GNumber of processor groupsgroups in the boot log
RCores deliberately left free (reserveCores)Config, default 0
t_ithreadCount of robot i in the arenaPrefab inspector
SThreads per physical core1 under the default spread policy

The shipped TrainingAreaVox holds one RL robot at threadCount 3 and one companion at 1, so C = 4 — which divides 32 exactly. That is not a coincidence; it is why those numbers were chosen.

Ask the code VxAff_MaxRepeats(pattern, n, &cfg) answers the same question using the real allocator, so it accounts for group boundaries and packing that the formula only approximates. Pass the arena's per-robot thread counts, e.g. {3, 1}.
Hard ceiling Fixed arrays throughout the DLL cap the scene at 128 robots total (g_is_Blow[128], g_RL_needs_reset[128], g_motorParams[128][1024], the render and physics buffers, and the robot file-name table). Remember the companion counts.

8 cores / 16 threads — a typical development machine

One group, P = 8. By the formula an arena costing 4 cores allows two arenas. In practice four arenas is the throughput optimum on this hardware, and the allocator prints [OVERSUBSCRIBED]. That warning is correct and you should accept it here.

  • 4 arenas × [3, 1] = 16 threads landing on 16 logical CPUs, one each. Nothing is double-booked; the fallback simply uses the SMT siblings the big-machine policy would have left idle.
  • Robots pair symmetrically — 0 with 4, 1 with 5 — matching thread counts as well as positions.
  • Dropping to two arenas would leave every sibling unused and lose real throughput.
  • The price is spare = 0: Unity's main thread shares a core with physics, so frames will jitter. At this core count there is no clean way around it.
Rule of thumb Above roughly 32 physical cores, treat [OVERSUBSCRIBED] as a defect to fix. At 16 or fewer, treat it as the expected state and check a different thing instead: that total threads ≈ logical CPU count, with no core carrying three or more.

Drop one arena from any of these rows to buy four spare cores for Unity. On hybrid chips (P-cores plus E-cores, such as a 16-core / 24-thread part) the allocator treats every physical core as equal, which it is not — take the row as a starting point and confirm with a throughput sweep rather than trusting it.

Threads Prefer more arenas over more threads per robot. A 33-voxel body gives each thread a few dozen elements of work per phase, against four OpenMP barriers per 1 ms micro-step — past 3 or 4 threads the synchronisation costs more than the work and the robot runs slower. Roughly: a few hundred elements per thread, minimum. Scaling wide beats scaling deep.

Keep the YAML identical across scenes. buffer_size counts total agent steps, so the number of policy updates at a given step count is the same either way — which is exactly what makes a 4-vs-16 comparison meaningful. Changing hyperparameters at the same time confounds the result.

Verify

You do not have to guess whether the layout worked. The allocator prints the whole assignment at boot; ten seconds of reading it replaces an afternoon of benchmarking. This is a healthy 64-core run, 15 arenas:

The baseline for a healthy training run: mode=ADAPTIVE, every robot spread, skipped=0, no PACKED, no [OVERSUBSCRIBED], and every processor group holding robots.

Confirming it in Task Manager

Performance ▸ CPU ▸ right-click the graph ▸ Logical processors. With one thread per core, only the even-numbered logical CPUs should be carrying physics load. Odd-numbered ones showing activity are Unity, Python and the OS using the siblings — that is exactly what the spare capacity is for. An older symptom worth recognising: the first half of the graph pinned and the second half flat means the process never reached the second processor group.

Unity's thread CPP_Pin_Caller_To_Spare_Cores(), called from the Unity main thread, parks it on the spare cores — the calling thread -> Group 1, 4 spare physical core(s) line above. It moves the main thread only; the render thread and Burst job workers stay unpinned. If it reports zero spare cores, drop an arena rather than ignoring it.

When it breaks

Troubleshooting

Failed to load PlayerSettings (internal index #0)
The build folder holds files from two different builds. Delete the output folder entirely and rebuild — Unity never cleans it for you. The bundled AutoBuilder now does this automatically.
The option engine_settings … is invalid
engine_settings is indented under the behavior. Move it to column 0, level with behaviors.
Observation size mismatch
BehaviorParameters disagrees with what CollectObservations writes. Nearly always a stale prefab value — see step 6. Confirm 240 (or 339 with angular velocity on).
Mean Reward stuck at exactly −0.200
That is −0.2 / 500 × 500: the time penalty alone, with every episode running to full length and no other term ever firing. The robot is not travelling. Check previousDistance in the agent's runtime state during Play — if it barely changes over 500 steps, the problem is actuation or body shape, not hyperparameters. Verify open-loop locomotion in Heuristic mode first.
"Target reached" fires when the robot is nowhere near the target
targetReachThreshold is in sim units. 0.2 means 2 metres, not 20 cm. Use 0.03 for Vox33.
Only part of the robot moves
muscleCount is smaller than the real number of muscle voxels. Voxels beyond the count keep a target of zero forever. Check it against the .vox file.
Nothing moves at all, and training never starts
The lock-step is stalled. VoxelRLManager waits for every agent to submit before stepping C++, so one agent with a missing Task Profile or a null manager reference freezes the whole scene. Check the console count matches the arenas you expect. Remember the first 1.5 s of silence is intentional.
Robot explodes or twitches violently
Lower TEMP_MAX in Apply_RL_Actions_To_Motors_Direct_Temperature_Control from 12 to 6–8 and rebuild the DLL. Early in training the policy is nearly random, and neighbouring voxels pulling in opposite directions is the worst case for a mass-spring solver.
Episodes end almost immediately
Flip detection is working, possibly too well. It compares the body's up axis against world up; if the forward or right voxel pair is ordered the wrong way the up axis is inverted from step one. Otherwise soften the check, or raise freezeStepLimit if the freeze test is the one firing.
Debug.Log lines missing from a standalone build's console
The console hook is attached in VoxelEngineCore.Awake(); anything logged before that never reaches the window. Check %USERPROFILE%\AppData\LocalLow\<Company>\<Product>\Player.log — if the line is there, it is a timing problem, not a missing call. Set VoxelEngineCore to −1000 in Script Execution Order, and put verification logs inside VoxelRLManager.InitializeRL(). Note the ServerMode executable has no console window at all.
[VxAff] … [OVERSUBSCRIBED]
Physical cores are exhausted and robot blocks now overlap. Because every robot is joined by the macro barrier, this slows down all of them, not just the overlapping ones. Reduce the arena count or the per-robot threadCount until cores used ≤ physicalCores. On a machine with 16 physical cores or fewer this warning is expected — see Machine recipes.
[VxAff] [SOME ROBOTS PACKED]
One or more robots could not find enough contiguous free cores and fell back to putting two threads on one physical core. The run is valid — packing costs only the robots it happened to — but it means you are close to the limit. Drop one arena, or lower threadCount so that the per-arena core count divides the per-group core count.
Group 1 : 0/32 cores used, 0 robots
Half the machine is idle. The allocator fills groups in order, so this means you simply asked for too few robots to reach the second group. Add arenas. If instead the robots are there but nothing is pinned, check that the DLL is the patched build — the old code computed the group as thread_id / 64, which is always 0.
16 arenas runs slower than 4
Almost always oversubscription: total threads exceeded physical cores, so the blocks overlap. Check cores used and spare in the assignment log rather than guessing. The second suspect is threadCount set too high for a small body — a 33-voxel robot gives each thread only a few dozen elements against four OpenMP barriers per micro-step.
OMP: Warning #182
Something set OMP_PROC_BIND. Don't — KMP_AFFINITY=disabled, which the compatibility layer sets before the first OpenMP call, already covers it. All pinning in this project is done explicitly by VoxCoreAffinity, because libomp does not handle Windows processor groups correctly.
Appendix

Moving to a bigger body

Once Vox33 trains, the next body in the project is maxFit_V516_M142.vox — 516 voxels, 142 muscles, a hollow box on four corner legs with a solid rigid top plate. Scenes Vox516_Single_Arena and Vox516_Multi_Arena_04 are set up for it. Three things change, and the third is the one people miss.

1. New landmarks, new constants

FieldVox33Vox516
expectedVoxelCount / muscleCount33 / 33516 / 142
centerVoxelIdx16239
forwardVoxelA / B17 / 1538 / 476
rightVoxelA / B21 / 11257 / 227
minSpawnDist / maxSpawnDist2.5 / 3.53.2 / 4.2
targetReachThreshold0.030.07
behaviorNameVoxBot33VoxBot516

The landmark voxels sit on the rigid top plate on purpose: a frame built from deforming voxels wobbles, and every observation wobbles with it. The pair order matters — swapping forwardVoxelA/B flips the derived up axis and every episode then ends on step one.

2. Observe a subset, not the whole body

296 of the 516 voxels are the rigid top plate. In the body-local frame their positions relative to the centre of mass are nearly constant — and normalize: true divides by the standard deviation, so a near-zero-variance channel gets amplified and saturated at ±5. Observing everything would give you 3 signal dimensions against roughly 1,776 amplified-noise ones.

The fix is observedVoxelIndices on the Body Profile: eight voxels, a foot and a mid-leg on each of the four legs. 

observedVoxelIndices = [0, 2, 68, 70, 438, 440, 506, 508]

obs = 9 + 6 × 8 + 142 = 199        # down from 3247
act = 142

Body posture is already carried by the local frame itself, so the top plate contributes nothing. Centre of mass and the local frame are still computed from all 516 voxels — that has to match the reward's reference — only the per-voxel observation loop uses the subset.

Inspector trap Setting Size to 8 fills the array with eight zeros. If you don't then type all eight values, the agent observes voxel 0 eight times, at the correct dimension count, with no warning. The shipped asset RobotBody_Vox516_Part already has them; RobotBody_Vox516 keeps full observation for A/B comparison.

3. Expect the action space to be the real bottleneck

142 independent continuous actions is a lot. Policy-gradient variance grows with action dimension, and ML-Agents starts with log σ = 0, so at step zero all 142 muscles draw independently across the full ±1 range — with CTE 0.02 × TEMP_MAX 12 that is a 24 % strain command each. Coherent gait emerging from that by chance is essentially impossible.

The cheapest remedy is to group muscles in the DLL — by leg and by height, say twelve groups — and index the action array by group id inside Apply_RL_Actions_To_Motors_Direct_Temperature_Control. Action drops from 142 to 12, and since the previous-action block shrinks with it, the observation drops to 69. The longer-term route is CPG modulation, where the policy shapes a fixed oscillator's amplitude and phase rather than commanding voxels directly.

Before you train Run the open-loop check on any new body. In Heuristic mode, can a hand-made sine gait move it 2 m in 20 s, and can it turn? If not, no amount of PPO will find a gait that doesn't exist, and half an hour here saves days.
